# Code Context

使用宿主环境提供的 HTTP 能力调用 Code Context v1 API。发起请求前阅读 [HTTP API 参考](references/http-api.md)，采用其中的默认服务地址，除非运行时配置覆盖。不要使用 MCP，也不要臆测其他端点或认证方式。

先检索并筛选代码，再根据保留下来的代码证据回答；不要以文件名、符号名或搜索摘要代替实现证据。

## 先规划，再批量检索

开始调用工具前，先在内部形成一个短检索计划：明确要回答的子问题、可能的入口/核心实现/配置/测试证据，以及哪些查询互不依赖。用户给出的信息足以开始时，不要先向用户确认搜索词、目录或实现猜想。

优先通过少量高信息密度的检索轮次完成任务。通常先进行一轮并行召回，再围绕筛选后的候选进行一轮并行补证；这是默认检索形态，不是轮数上限：

1. **并行召回。** 第一轮同时发起互补且独立的查询，而不是等待一个结果后才想下一个关键词。通常组合精确符号名、业务词或字符串、入口/API、配置项、异常或日志文本；已知范围时立即添加 `path` 或 `globs`。所有请求项都指定 `repo_id`。
2. **筛选候选。** 根据命中位置、符号容器、片段内容和与问题的因果距离去重并排序。优先保留入口、实际实现、关键分支和数据变换；降低生成代码、重复声明、无关测试夹具和仅同名命中的优先级。不要对所有命中逐个读取。
3. **并行补证。** 只围绕高价值候选，一次并行取得回答所缺的上下文，例如符号上下文、文件局部、定义/引用、调用关系、实现类、相关配置或能说明行为的测试。语义导航前使用准确且从 1 开始的 `file`、`line` 和 `column`。
4. **证据闭环后作答。** 当代码已能支持“入口 → 关键实现/分支 → 结果”的解释，并覆盖回答所需的关键子问题时，停止检索并直接回答。若仍缺少关键证据，或存在歧义、冲突、动态分派和多实现等情况，则继续进行窄范围检索，直到形成证据闭环。轮数是效率目标，不是停止条件；不要为了穷尽仓库而继续搜索。

同一阶段内没有数据依赖的调用应并行执行；只有后一步参数必须来自前一步结果时才串行。优先批量规划完整的一轮查询，减少“搜一次、读一次、再想一次”的模型交互。

同一工具的独立查询合并到一次 `POST /v1/tools/{tool_name}` 的 `requests` 数组中；不同工具必须调用各自端点，但可由宿主并行发出。批次不要超过服务端限制，也不要把后续参数依赖当前结果的查询提前塞入同一批次。按请求顺序核对 `results`，逐项处理 `error` 和 `truncated`。

## 检索与筛选技巧

- 从用户问题提取多种独立锚点：精确类/方法名、领域名词、路由或注解、配置键、常量值、日志和异常文本。用它们并行交叉定位，避免只依赖一个宽泛词。
- Java 明确符号优先用 `search_symbols`；业务词、字符串和正则用 `search_code`。两者可在第一轮并行互证。其他语言以 `search_code`、`list_files` 和 `read_file` 为主。
- 像使用 `rg` 一样构造高信号查询：优先精确字面量或少量备选的正则；已知模块、语言或文件类型时用 `path`/`globs` 收窄，必要时排除生成目录、vendor、构建产物或快照。
- 若命中过多，按模块、文件类型、符号容器或更独特的相邻文本收窄；若没有命中，再依次尝试命名变体、调用方术语、配置/日志文本或有限的目录浏览。不要一开始就读取大文件或遍历整个仓库。
- 搜索片段用于筛选，不一定足以作答。对最终采用的关键候选读取覆盖完整逻辑分支的局部代码；需要确认跨文件行为时，再跟随精确定义、引用、`call_sites` 或调用路径。
- 测试适合验证预期行为和边界，但实现代码是说明当前机制的主要证据。若测试与实现看似冲突，明确指出并用 Git 上下文或进一步的精确检索消解。

## 选择代码仓库

- 新服务仓库 ID：`easy-rent-contract`。绝大多数业务流程位于新服务；没有更明确线索时优先检索这里。
- 老服务仓库 ID：`home-trusteeship-contract`。大多数流程已迁移到新服务，目前主要负责：
    - 对外 Dubbo 接口；所有提供给外部系统的 Dubbo 接口都在老服务。
    - 聚合多个下游或领域结果。
    - 合同列表页逻辑。
    - 合同详情页的部分逻辑。
    - 尚未迁移的部分计算逻辑。
- 用户明确指定仓库时遵从用户选择。若指定范围明显无法覆盖问题，说明原因后补充检索另一仓库。
- 问题涉及对外接口入口、跨服务调用或迁移边界时，同时检索两个仓库。
- 新老服务存在同名逻辑或 API 时，以新服务实现为准；老服务用于说明入口、适配、聚合或兼容行为。
- 最终回答必须列出实际检索过的仓库，并简要说明选择原因。没有实际调用工具的仓库不得声称已检索。

## 工具选择

- `search_code`：文本或 ripgrep 正则检索，返回可直接阅读的代码片段。
- `search_symbols`：按名称检索 Java 类型、方法或字段，返回符号类型、所属容器和精确位置。
- `find_definition`、`find_references`、`find_overrides`：Java 符号导航。
- `get_type_hierarchy`：Java 父类型或子类型；`get_call_graph`：入向或出向调用关系。
- `trace_call_path`：已知起点和目标符号时查找一条调用路径。
- `get_file_symbols`、`get_symbol_context`、`read_file`：理解文件或符号上下文。
- `list_files`：浏览仓库结构；`git_query`：查询只读 Git 历史、差异或状态。

语义工具当前由 JDT LS 提供，仅用于 Java。其他语言使用 `search_code`、`read_file`、`list_files` 和适用的 `git_query`。

## 调用关系

直接关系使用 `depth: 1`；业务流程追踪通常使用 `depth: 2` 或 `depth: 3`。仅在确有必要时增加深度，因为节点数量会快速增长。跟随工具返回的精确位置和 `call_sites`，不要仅凭同名符号推断调用链。

## 回答要求

先给出问题的直接结论，再用筛选出的代码说明关键流程、条件和结果。引用仓库相对文件路径及尽可能精确的行号；区分代码明确事实与根据多处证据作出的推断。若检索受 `error`、`truncated`、非 Java 语义能力或缺失实现限制，应说明范围，不把未命中表述为不存在。

检查每次调用的 `error` 和 `truncated`。结果被截断时，缩小 `path`、`globs`、查询表达式或 `depth` 后重试；降低 `limit` 本身不会让缺失结果变完整。
